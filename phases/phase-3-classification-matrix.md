# Phase 3 — Classification & Matrix

## Objective
Replace both remaining Phase 1 stubs with real implementations behind the exact same call signatures: `StubClassifier` → real Gemini 2.5 Flash classification, and the worker-internal stub matrix (`app/services/matrix.py`'s hardcoded `_STUB_ROWS`) plus the API-facing fixture-backed `StubMatrix` → a real Sheets-backed reader of the client's live `Sheet1` pivot grid, with a Redis TTL cache, version hashing, and a working admin refresh. No route, schema, or business-rule change — same pattern as Phase 2's adapter swap.

## Context
`GEMINI_API_KEY` and `GOOGLE_SHEET_ID`/`GOOGLE_SERVICE_ACCOUNT_JSON` are confirmed real and set in `.env` (the project owner replaced an earlier placeholder Gemini key partway through this project). This environment has no network access to call the real Gemini or Sheets APIs — build and test against fakes per `docs/conventions.md` → Testing. Manual smoke checks against the real APIs happen outside this session, exactly like Phases 2's Drive/Supabase checks.

**Read first:** `docs/ai-integration.md` §1 in full (model, input, structured output shape, system instruction verbatim, decision logic, failure handling), `docs/schema.md` §2 (the pivot-grid matrix structure) and §3 (Redis keyspace: `matrix:data`, `matrix:version`, `lock:matrix:refresh`, `MATRIX_CACHE_TTL`), `docs/business-rules.md` §5 (matrix version hash calculation), `app/services/classifier.py` and `app/services/matrix.py` (the exact interfaces being replaced), `app/worker/tasks.py`'s `_do_classify_body` and `_resolve_and_submit` (the only two call sites), `scripts/validate_matrix.py` in full (the pivot-grid parser already built and validated against the client's real sheet in Phase 0a — **do not re-derive this parsing logic; extract and reuse it**).

> **Important scope note**: `scripts/validate_matrix.py` already contains a fully-working, already-validated-against-the-real-sheet parser (`parse_pivot_matrix`, `HEADER_TO_JEWELRY_TYPE`, `CATEGORY_LABELS`, `STYLE_LABELS`, `REFERENCE_URL_RE`, `_split_prompt_and_url`, the `Variant` dataclass). This phase's Sheets matrix reader must reuse this exact logic, not reimplement it — the client's sheet layout is genuinely unusual (hand-authored pivot grid, not a flat table) and re-deriving the parser risks subtly diverging from the already-validated one. Extract the parsing logic into a shared module (e.g. `app/services/matrix_parser.py`) importable by both `scripts/validate_matrix.py` and `app/services/matrix.py`, and update the script to import from there instead of duplicating.

## Step 1 — Real Gemini Classifier

### What to do
Implement the real classifier behind the same interface `app/worker/tasks.py` already calls (`ClassificationResult`, `Prediction` — do not change these dataclasses' shape, only what produces them):

- Add a `Classifier` `Protocol` to `app/services/classifier.py` (mirroring the `GenerationProvider`/`StorageAdapter` pattern): `async def classify(self, image_bytes: bytes) -> ClassificationResult`. `StubClassifier` already satisfies this shape — keep it as-is, it remains the test fixture.
- `GeminiClassifier` — real implementation using `google-genai` (already pinned, `google-genai==0.3.0`). **Before writing any Gemini API calls, introspect the actually-installed package** (`python -c "import google.genai; print(google.genai.__file__)"`, then read its source / `help()` output, or check `site-packages/google/genai/`) rather than assuming a specific API surface from general knowledge — SDK versions in this exact family have changed their client/config API repeatedly, and guessing wrong wastes a whole implementation cycle. Confirm the actual client construction pattern, the actual structured-output/response-schema mechanism, and the actual image-input mechanism (inline bytes vs. a file/Part object) against what's installed, then build against that.
- **Model**: `settings.gemini_model` (default `gemini-2.5-flash`).
- **Input**: the raw source image bytes (already fetched by the worker's `_do_classify_body` before calling `classify()` — no re-encoding). No prompt-matrix context passed in (must not bias the classifier — `docs/ai-integration.md` is explicit about this).
- **System instruction**: use the exact verbatim text from `docs/ai-integration.md` §1 → "System instruction (verbatim)". Do not paraphrase or shorten it.
- **Structured output**: constrain the response to the exact schema in `docs/ai-integration.md` §1 (`is_jewelry: bool`, `predictions: list[{jewelry_type: JewelryType enum, confidence: float}]` — exactly 3, descending by confidence, `notes: str` for debug only). Use the SDK's actual structured-output mechanism (response schema / JSON mode — whatever the installed version actually calls it) rather than parsing free text.
- **Timeout**: 15s per `docs/ai-integration.md` §4's Cost & Safety Controls table. Confirm how to set a request timeout with the installed SDK version.
- **Decision logic** stays in the worker (`app/worker/tasks.py`'s `_do_classify_body` already implements the `is_jewelry`/threshold/`needs_input` branch correctly against `ClassificationResult` — **do not duplicate or move this logic into the classifier itself**; `GeminiClassifier.classify()` only returns the raw `ClassificationResult`, exactly like `StubClassifier` does today).
- **Failure handling**: per `docs/ai-integration.md` §1's table — API error/timeout, malformed/schema-violating output, and safety blocks are all things `GeminiClassifier.classify()` should raise a plain exception for (the existing `retry_free` wrapper around the call site in `_do_classify_body` already handles the 3×/2s-8s-30s retry — **do not add a second retry layer inside `GeminiClassifier` itself**, that would double the actual retry count against the real API). "Type not in enum" shouldn't happen with a proper structured-output schema constraining the enum server-side — if the installed SDK version can't actually enforce an enum constraint at generation time (some structured-output implementations only support JSON *shape*, not literal-value constraints), validate and discard any out-of-enum prediction client-side, and if none of the 3 predictions are valid, treat it as equivalent to `needs_input` (there's no clean way to synthesize `candidate_types` from zero valid predictions — least-bad option: raise, letting the retry loop try again, and if retries are exhausted, this surfaces as `CLASSIFIER_ERROR` same as any other malformed-output failure. Document whichever choice you make).
- **Never log**: image bytes, base64 payloads, the API key. **Always log** (per `docs/ai-integration.md` §4): `job_id` (already bound via the worker's logging context), model name, latency_ms, outcome, top confidence.
- Add a `get_classifier() -> Classifier` factory in `app/services/classifier.py` (mirroring `app/providers/factory.py`/`app/storage/factory.py`'s pattern) that unconditionally returns `GeminiClassifier()` in real code, and update `app/worker/tasks.py`'s `_do_classify_body` to call `get_classifier().classify(...)` instead of instantiating `StubClassifier()` directly. Tests monkeypatch `get_classifier` (or `app.worker.tasks.get_classifier`) to return `StubClassifier()` or a custom fake — mirroring exactly how `tests/test_worker_tasks.py` already monkeypatches `get_provider`.

### Checkpoint 1

**Testing strategy note**: unlike `FakeDriveClient`/`FakeSupabaseStorageClient` (which fake a whole Protocol this project defined itself), Gemini's actual wire format is a third-party SDK's concern. Two reasonable approaches: (a) fake at the `Classifier` Protocol boundary — i.e. `GeminiClassifier`'s *internal* Gemini-SDK-calling method is separated from a thin wrapper, and tests inject a fake SDK client object satisfying whatever minimal surface `GeminiClassifier.__init__` accepts (mirroring `GoogleSheetsClient`/`GoogleDriveClient`'s constructor-injected-client pattern used elsewhere in this codebase); or (b) test `GeminiClassifier` only at the `Classifier` Protocol level using `StubClassifier`-equivalent substitution everywhere except one narrow unit test of `GeminiClassifier`'s response-parsing helper (schema dict → `ClassificationResult`), with the actual SDK call itself left effectively untested until the live smoke test. Prefer (a) if the installed SDK's client is reasonably injectable (constructor-injected, like `GoogleSheetsClient`/`GoogleDriveClient` already do); fall back to (b) if the SDK makes that awkward. Use your judgement, document the choice.

## Step 2 — Real Sheets Matrix Reader

### What to do
1. **Extract the shared parser**: move `scripts/validate_matrix.py`'s parsing logic (`Variant`, `HEADER_TO_JEWELRY_TYPE`, `CATEGORY_LABELS`, `STYLE_LABELS`, `REFERENCE_URL_RE`, `_split_prompt_and_url`, `parse_pivot_matrix`) into `app/services/matrix_parser.py`. Update `scripts/validate_matrix.py` to import from there instead of defining its own copy — run the script's own logic (if it has tests, or at minimum confirm `ruff`/`mypy` pass on it afterward) to confirm nothing broke in the extraction.
2. **Real matrix read + cache** in `app/services/matrix.py`, replacing the hardcoded `_STUB_ROWS` dict and the fixture-backed `get_matrix_response()`:
   - `async def refresh_matrix(redis, sheets_client, sheet_id, tab="Sheet1", *, force: bool = False) -> tuple[str, int, bool]` (or similar — matches `MatrixRefreshResponse`'s `matrix_version, rows_loaded, changed` shape already defined in `app/api/v1/admin.py`): reads `Sheet1` via `sheets_client.read_all_rows` (reuse `SheetsClient` Protocol from `app/store/sheets_store.py` — same client, read-only in practice since this only calls `read_all_rows`), parses via the extracted `parse_pivot_matrix`, computes the matrix version hash per `docs/business-rules.md` §5 ("sha256 of all active matrix rows serialised in sorted key order, truncated to 16 hex chars"), and writes `matrix:data` (serialised JSON of all variants) and `matrix:version` to Redis with `MATRIX_CACHE_TTL` (`matrix:data`) — check `docs/schema.md` §3 for which keys have a TTL and which don't (`matrix:version` has no TTL listed, `matrix:data` does, at `MATRIX_CACHE_TTL` seconds). `changed` = whether the newly-computed version differs from what was previously cached.
   - Use `lock:matrix:refresh` (30s TTL, per `docs/schema.md` §3) to prevent a thundering-herd re-read when many requests miss the cache simultaneously — mirror `app/store/sheets_store.py`'s `_with_lock` pattern (same `SET NX EX` + retry-sleep approach) if it fits, or a smaller local equivalent.
   - `async def resolve_matrix_row(jewelry_type: JewelryType, service: ServiceType) -> MatrixRow | None` — reads from the Redis cache (`matrix:data`), refreshing first if the cache is cold/expired (this needs access to `redis`/`sheets_client`/`sheet_id`, which the current stub signature doesn't take — **this is a signature change from the Phase 1 stub, which is fine and expected since Phase 3 explicitly replaces this stub**; update the two call sites in `app/worker/tasks.py` accordingly, threading through whatever context — `ctx["app_redis"]`, a sheets client, `settings.google_sheet_id` — the worker already has available in scope at its call site). Per the client's sheet having multiple prompt variants per `(jewelry_type, service)` combination, **pick one at random per resolve** (already noted as a deliberate client decision in `docs/schema.md` §2 — use `random.choice` or similar over the matching variants).
   - `def current_matrix_version() -> str` (or async, matching whatever `resolve_matrix_row`'s access pattern needs) — reads the cached `matrix:version` key; if cold, triggers a refresh first.
   - `async def get_matrix_response() -> MatrixResponse` — replaces the fixture-backed stub. Builds the `MatrixResponse` (`matrix_version`, `cached_at`, `combinations`, `jewelry_types`, `services`) from the same cached real data, **never including prompt text** (already structurally guaranteed if `MatrixResponse`'s schema has no prompt field — confirm this is still true after wiring in real data, since now there's real prompt text in memory that must not leak into this specific response path).
3. **Wire the real admin refresh**: `app/api/v1/admin.py`'s `POST /admin/matrix/refresh` currently returns a hardcoded stub (`rows_loaded=0, changed=False`). Replace its body to call the new `refresh_matrix(..., force=True)` (bypassing `MATRIX_CACHE_TTL`, per `docs/api-routes.md`'s description: "Force an immediate re-read... bypassing the TTL") and return the real result. This route needs a `SheetsClient` instance — mirror how `app/api/v1/generate.py` and `app/worker/settings.py` already build one (`GoogleSheetsClient(settings.google_service_account_info)` in a try/except, or however the existing pattern handles a Sheets-unavailable case; check both call sites for the established convention before picking one).
4. **Matrix Coverage caveat**: `docs/business-rules.md` → "Matrix Coverage" section is an explicitly-flagged point-in-time snapshot with two known data-quality issues in the live sheet (row 16 missing prompt text, row 23 missing a reference URL) and several zero-variant combinations. Per that section's own instruction, **re-run `python scripts/validate_matrix.py` against the real sheet as part of this phase's verification** (this session has no network access to do so live — flag this as a manual step for the project owner, same pattern as Phase 2's live smoke tests) before treating the coverage table as current. Do not "fix" the two data-quality issues in code (e.g. don't invent a fallback prompt or a fallback reference URL) — a `MATRIX_MISS`-adjacent partial row is a content gap for the client, not a bug to route around (R9's spirit applies even to partially-populated rows).
